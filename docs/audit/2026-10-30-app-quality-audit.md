## 1. ペアリングエンジン（src/engine/pairing.ts）

### 1-1. 数値スコア・成分の単純合算による予測 — **問題なし**
- `analyzePairing` の返り値は level／共通ノート／共通分類／対比／メッセージのみで、数値スコアのフィールドは存在しない。単体テストにも「score プロパティを持たない」「『N点』パターンを含まない」検証がある（pairing.test.ts）。
- 強度の `rank()` は順序尺度（弱い1・普通2・強い3）の閾値フィルタ（normal以上を「既知」とみなす）と対比抽出（strong のみ）に使うだけで、化合物濃度や強度の合算による相性予測はしていない。
- 味覚の対比は両方に記録がある場合に「並置」するだけで、合成値を作らず、文面にも「組み合わせたときの変化は検証されていません」と明記されている。

### 1-2. recommend() の内部ソートキー — **要検討**
- `recommend` は調和型で `共通ノート数×10＋分類重なり数`、対比型で `-分類重なり数×10＋ノート数` という内部キーで候補を並べ替える。これは数値として画面に出ず、全候補が落ちない（テストで件数保持を確認）うえ、画面にも「相性の良し悪しではなく探索の手がかり」と注記があるため原則違反ではない。
- ただし「共通点の個数で順位付けする」こと自体は、禁止事項である単純合算の近傍にある。現状の注記を維持し、順位が品質含意を持たないことを崩さないこと。

### 1-3. フレーバーホイールの面積表現 — **要検討**
- FlavorWheel は大分類の弧の大きさを「その分類に属するノートの順序尺度ランクの合計」に比例させている。これは予測やスコアではないが、弧の面積が「記録されたノートの数と強さの合計」で決まるため、データ収録量が多い分類ほど大きく見え、香りの実際の卓越度と誤読される余地がある。

### 1-4. evidenceLevel の画面までの一貫性 — **問題なし（一部 要検討）**
- 一覧・詳細では `LEVEL_LABEL`（実測・官能評価あり／一般的な知見／探索的な予想／情報不足）バッジ、詳細では項目ごとの `BASIS_LABEL`（実測／官能評価／総説による整理／一般的知見）、組み合わせ画面では結果レベルバッジと、区分表示は画面まで一貫している。
- 組み合わせ結果は exploratory か insufficient のみを返し、実測・官能評価ありを名乗ることはない（保守的で正しい）。
- 現在、全19アイテムの item レベル evidenceLevel が一律 `general` で、`measured` は item レベルでは使われていない。項目レベルでは basis=measured/sensory のエントリ（ミルク・単叢・ダーク等）があり、詳細画面の BASIS_LABEL で補完されているため過大表示にはなっていないが、item バッジだけ見ると実測エントリのあるアイテムも「一般的な知見」としか分からない。

### 1-5. 「情報不足」判定の残存 — **要検討**
- エンジンの insufficient 分岐は残っており、合成した空プロファイルでの単体テストで検証されている。
- しかし現在の実データでは、全19アイテム（お茶14・チョコ5）が normal 以上の香りを1件以上持つため、**実データ同士の組み合わせでは insufficient は発生しない**。PairPage の初期選択・全候補でも到達しない。
- 画面上で「情報不足」が実際に現れるのは、時間変化（鳳凰単叢の余韻以外は全アイテム未収録表示）と味覚（全アイテム unknown 表示）の領域のみ。これは仕様違反ではないが、ペアリング結果の情報不足は合成データ依存の検証になっている点を認識しておくべき。

## 3. 保存機能（src/storage.ts と SavedPage）

### 問題なしの点
- `validateSaved` は非オブジェクト・バージョン不一致・文字列でない要素を含む配列を例外で弾き、`loadSaved` は JSON.parse の失敗を含む全例外を捕捉して空データにフォールバックする。
- 復元（import）側も JSON.parse＋validateSaved を try/catch で囲み、失敗時は `role="alert"` でエラーメッセージを表示する。壊れたJSON・型不一致はアプリを落とさない。
- テストは null／バージョン99／数値混入配列／履歴の重複排除と上限20をカバーしている。

### 要検討（軽微な穴）
1. `importJson` の `f.text()` の失敗（ファイル読み取りエラー）が未処理で、失敗時に何も表示されず未処理の Promise rejection になる。
2. `persistSaved`（useEffect 内の localStorage 書き込み）は例外を捕捉していない。容量超過やプライベートモード等で setItem が投げた場合に備えた try/catch がない。
3. 復元データの重複IDは除去されず、履歴の上限20も復元時には適用されない（上限は pushHistory 経由の追加時のみ）。表示上の実害は小さい。
4. `loadSaved` の「localStorage 内の壊れたJSON」ケース自体を検証するテストがない（validateSaved の異常系テストで実質カバーされているが、loadSaved 経路は未テスト）。
5. 未知のID文字列も検証を通る（表示側は生IDにフォールバックするため無害）。

## 4. アクセシビリティ

### 問題なしの点
- フレーバーホイール: SVG セグメントが `tabIndex={0}`・`role="button"`・`aria-label` を持ち、Enter/Space で操作可能。加えて同じ操作ができるチップボタン一覧（`<ul>`＋`<button>`）が併設され、キーボード・支援技術の代替経路がある。
- 検索 input に aria-label、お気に入りボタンに aria-pressed、タブに role=tab／aria-selected、復元エラーに role=alert、ノート詳細に aria-live="polite" がある。
- TasteChart は role="img"＋aria-label で、バーは aria-hidden、値そのものはテキストでも表示される（色だけに依存しない）。
- App.css に `:focus-visible` のアウトライン（3px）があり、`@media (prefers-reduced-motion: reduce)` で animation/transition を無効化している。

### 要検討
- PairPage の tablist は role=tab のみで、対応する tabpanel／aria-controls の関連付けがない。
- ホイール SVG は `role="img"` を持ちながら内部にフォーカス可能な role=button 子要素を含む。支援技術によっては img ロール配下の対話要素の扱いが一貫しない可能性がある（チップ一覧の代替経路があるため実害は限定的）。

## 5. GitHub Pages 対応

### 問題なしの点
- vite.config.ts は `base: './'` の相対指定で、プロジェクトサブパス（/pairing/）でもアセット解決が壊れない。
- ルーティングは location.hash ベースの手書きハッシュルーティング（parseRoute＋hashchange リスナ）。URLパス自体が変わらないため、詳細画面（#/tea/sencha 等）への直接アクセス・リロードでも Pages の 404 にならない。
- アプリが生成する URL はすべてハッシュ内のみで、Pages で 404 になるパス遷移は存在しない。

### 要検討
- 未知のハッシュ（例: #/bogus）は main が空表示になる。フォールバック表示がない（実害は小さい）。
- PairPage の初期選択が `teaItems[6]` のような配列位置依存で、データ追加で初期ペアが意図せず変わる fragility がある（現状は烏龍茶）。
